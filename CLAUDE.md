# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Flask marketing site for Caribbean Incentive, a boutique Caribbean DMC (destination management company). The full functional/content spec — every route, every piece of client copy, and the five "interactive modules" — lives in `CLAUDE_CODE_BUILD_PROMPT.md`. Read that file before making any content or structural change; it is the source of truth for content and behavior. The *visual* design has since been rebuilt as a cinematic editorial site and no longer follows that file's Bootstrap/design-token section (see "Front end" below).

## Commands

```bash
python -m venv venv
venv\Scripts\activate          # Windows
pip install -r requirements.txt
copy .env.example .env
python app.py                  # runs on http://127.0.0.1:5000, debug follows FLASK_DEBUG
```

There is no test suite, linter, or build step configured in this repo.

Demo imagery: `python scripts/fetch_curated_images.py` overwrites every slot in `content/media.py` with a hand-picked, on-theme Unsplash photo. (`scripts/fetch_placeholders.py` is the older hashed pool — it only fills missing files and produced off-brand repeats; prefer the curated script.)

## Architecture

**Content is separated from templates.** Every piece of copy, nav structure, pricing constants, and per-island data lives in `content/*.py` as plain Python dicts/lists/tuples — never hardcoded in Jinja. Routes in `routes/main.py` import from `content/` and pass it straight into `render_template()`. When asked to change copy, edit `content/`, not `templates/`. Copy may contain `**bold**` markers; render those with the `md_bold` filter (registered in `app.py`), which escapes everything else.

**Media indirection.** `content/media.py` holds a single `MEDIA` dict mapping logical keys (e.g. `"island.saint-martin.hero"`) to paths under `static/`. Templates never hardcode an image path — they call the Jinja global `img('key')`. `NAV` items in `content/site.py` also carry an `image` media key used by the full-screen menu preview.

**App factory + blueprints.** `app.py` defines `create_app()`, registers `routes/main.py` (pages), `routes/inquiry.py` (three `/inquiry/*` POSTs) and `routes/admin.py` (demo admin — see "Admin" below), and injects global context (nav, footer, contact, brand descriptor, tagline, marquee lines, CTA band copy, island list).

**Forms submit in place, not via redirect.** `routes/inquiry.py` handlers re-render `connect.html` directly on success and validation failure, passing `brief_success` / `rfp_success` / `callback_success` plus `active_tab`. Do not change these to redirects. `connect.html` shows server-side field errors inline and supports deep links to a tab (`/lets-connect#tab-rfp`).

**Mail goes out through Microsoft Graph.** `services/graph_mail.py` (stdlib, client-credentials flow against the Azure app registration) is the transport whenever `GRAPH_TENANT_ID` / `GRAPH_CLIENT_ID` / `GRAPH_CLIENT_SECRET` / `GRAPH_SENDER` are all set; the Gmail `MAIL_*` SMTP path in `services/mailer.py` is now only a fallback, and the local archive catches everything else. Graph sends a single HTML body (no multipart), so the plain-text twin is kept for SMTP and the archive, and an attachment over ~3 MB is dropped from the message rather than failing the send — the RFP still reaches Supabase and the admin. The app needs the **application** permission `Mail.Send` with admin consent, scoped to the one mailbox with `New-ApplicationAccessPolicy`. `python scripts/graph_mail_test.py` checks config, token and mailbox and translates the AADSTS codes; `--send <address>` delivers one real message.

**Contact details have one source.** `content/site.py` `CONTACT` (address, phone, `RFP_EMAIL`) feeds the pages, and `services/mailer.py` reads `OFFICE_ADDRESS` / `OFFICE_PHONE` / `OFFICE_EMAIL` / `TAGLINE` straight from it — change the client's details there only. Note the two domains: the site and mail now use **caribbean-incentive.com** (Microsoft 365, which is what `GRAPH_SENDER` sends as); `caraibes-incentive.com` is the French-market domain, hosted at IONOS, and is no longer referenced in the app.

**Outbound email is one hand-built template.** `services/mailer.py` renders both messages (team notification + sender acknowledgement) as 600px table HTML with inline styles, in the site's palette/type, plus a plain-text twin. It prints **only what a human needs to answer**: storage plumbing (`File URL`, `File path`, `File type`, `File size`, bucket paths — see `INTERNAL_FIELDS`) is never shown, the document goes as an attachment, and a signed link appears only as one "Download document" button. Contact fields are lifted into the navy "From" panel, the rest render as the detail list. `python scripts/preview_emails.py` writes every variant to `instance/email_preview/` without sending.

**WhatsApp alerts run on the Meta Cloud API.** `services/whatsapp.py` sends every brief, RFP and callback to `WHATSAPP_TO`, formatted for a phone: header + reference + timestamp, the contact as one block (name — company, e-mail, phone), then the request fields, with long free text on its own line. It reuses `services/mailer.py`'s `INTERNAL_FIELDS` / `CONTACT_FIELDS` / `_human_size()`, so storage URLs, bucket paths, MIME types and byte counts are filtered out of both channels by one rule — an RFP alert shows the document name and human size only. Meta only delivers free-form text within 24 hours of the recipient's last inbound message, so outside that window it must send a template: `ci_new_enquiry` (UTILITY, en_US) takes the five positional values `_template_params()` builds — type, reference, name, company, contact — and is enabled by setting `WHATSAPP_TEMPLATE=ci_new_enquiry`. Template bodies may not start or end with a placeholder. `python scripts/whatsapp_test.py` prints the sender, its quality rating and every template's approval status; `--send` delivers one real test alert. Blank credentials archive to `instance/whatsapp_outbox.jsonl`.

**Every human-facing timestamp is shown in AST, not UTC or server-local.** `services/store.py` defines `AST = timezone(timedelta(hours=-4), name="AST")` — Saint-Martin's real offset, fixed year-round since it never observes daylight saving. The admin lists' `submitted_at` (`store.py`), the e-mail masthead stamp (`services/mailer.py`) and the WhatsApp alert stamp (`services/whatsapp.py`) all convert through this one constant before formatting, so the team never has to convert UTC in their head regardless of what timezone the server itself runs in (Vercel is UTC). Storage stays UTC throughout (reference IDs, `created_at`, archive timestamps) — only the final display converts. Import `AST` from `services.store`, don't redefine it.

**Sellsy/Mail have local fallbacks by design.** Missing credentials log and write to `instance/submissions.jsonl` / `instance/rfps/` while still reporting success. Preserve this. Sellsy is live (API v2, `services/sellsy.py`, `send_to_sellsy(kind, reference, fields, ...)`): every brief, RFP and callback finds-or-creates the company (by name, as a prospect) and contact (by e-mail), then — per the client's mapping (Oct 2026) — **only RFPs become pipeline opportunities** (configured `SELLSY_PIPELINE_ID/STEP_ID/SOURCE_ID`, document attached); **event briefs (form and chat) and callback requests become Sellsy tasks** (`TASK_ACTIONS`: "Schedule meeting" due in 24 h, "Call back" due in 4 h, label `SELLSY_TASK_LABEL_ID`, assigned to the owner, linked to the company — Sellsy tasks reject a contact link, so the person's details live in the title and note). Do not turn briefs or callbacks back into opportunities. All on a background thread; failures fall back to the local archive. `_push` returns `(record type, id)`. Every website record is marked as from the website: the name/title starts with 🌐, RFP deals also get the Sellsy smart tag `Website` (`WEBSITE_TAG`; tagging failures only log), and the note/description opens with a "🌐 FROM THE WEBSITE" block built in the request by `services.visitors.lead_context()` (domain, channel: Let's Connect form vs chat assistant, AST time, page, then the visitor's journey read by the `ci_vid` cookie: traffic source, landing page, visits/pages, first visit, location, device, top modules) above "FORM DETAILS". `send_to_sellsy(..., channel=...)` carries the channel; `dispatch_brief` sets it from `source`. Demo records pushed to Sellsy are listed in `instance/sellsy_demo_records.json` for cleanup.

**The chat widget has two AI modes, both on one model through OpenRouter via LangChain.** `POST /chat` (`routes/chat.py`) takes `{messages, mode, confirm}`; every key stays server-side. `services/gemini.py` is the one place that knows the provider — `ChatOpenAI` pointed at OpenRouter's OpenAI-compatible endpoint (`https://openrouter.ai/api/v1`) — so `services/ask.py` and `services/project_assistant.py` only ever call `gemini.chat_model()` / `.to_messages()` / `.response_text()` and never touch a provider SDK directly; swapping providers again means editing that one file, not the two feature modules. **Never point `OPENROUTER_MODEL` at a `:batch` model id** — those are asynchronous (minutes-to-24h turnaround) and the chat widget needs a synchronous reply; `model_name()` strips a `:batch` suffix and logs a warning if one slips into the env var anyway.

- **Ask Caraïbes** (`mode: "ask"`, `services/ask.py`) — retrieval-augmented Q&A. `services/knowledge.py` builds one in-process BM25 index over the site knowledge (`services.chatbot.KNOWLEDGE`, rendered from `content/*.py`) plus any `.pdf`/`.txt`/`.md` in `knowledge/` (`KNOWLEDGE_DIR`); French queries are expanded through a small `FR_EN` term map because the corpus is English. **No vector database** — do not add one unless the corpus outgrows a few hundred chunks. The prompt forbids invention; cost questions must go through the bound `estimate_trip` tool, which is the existing `content.pricing` calculator (`services.chatbot.run_estimate`) — never add a second estimator. Without `OPENROUTER_API_KEY` it falls back to `services/chatbot.py` (Claude, then offline keywords).
- **Project Assistant** (`mode: "project"`, `services/project_assistant.py`) — slot-filling toward an event brief. Each turn re-extracts the whole transcript into the `ProjectBrief` schema (structured output via `.with_structured_output()`, temperature 0), so **conversation state lives in the transcript and values are never taken from the client**; a forged `brief` in the payload is ignored. When no `REQUIRED` slot is missing it returns the summary plus the confirmation question and `ready: true`. It submits **only** on a follow-up request carrying `confirm: true` — sent exclusively by the widget's "Submit my brief" button, never inferred from an affirmative sentence. Before submitting it validates through the real `EventBriefForm` and maps the conversation onto the form's fixed choices (`_request_type`, `_budget_band`).
- Both the `/inquiry/brief` form and a confirmed chat brief dispatch through `services/leads.py` (`dispatch_brief`) — one reference format, one path to mail, WhatsApp, the database, Sellsy and visitor conversion. Add new brief channels there, not in the route.
- Model id: `OPENROUTER_MODEL`, default `google/gemini-3.6-flash` — a normal (non-batch) OpenRouter model id, same price as calling Google directly since OpenRouter adds no markup on this one. (Project history: this ran on `langchain-google-genai` straight against Google's API through Oct 2026; moved to OpenRouter by the client's own choice, not for cost or latency — both were equal or worse through the extra hop. If OpenRouter is ever dropped, reverting is: swap `ChatOpenAI`→`ChatGoogleGenerativeAI` and the env var names in `services/gemini.py` only.)

**Estimator math must match a fixed worked example.** The client model (Sept 2026) is `(island base rate x nights x tier multiplier) x 1.12 + add-ons = per person`, `x group size = program total`; the 1.12 is a flat 12% on-site programme management fee. `content/pricing.py`'s `estimate()` and `static/js/estimator.js` must both produce **$1,958 per person / $117,480 total** for Saint Martin, 60 people, 4 nights, Premium, transfers + boat + gala + décor. Verify against this case if you touch either. Rates live in `ISLAND_RATES` (Saba is priced but has no destination page — the estimator pills come from this list, not from `content/islands.py`), tiers are Essential/Premium/Signature multipliers, and page defaults are 60 people, 4 nights, Premium.

**No island is labelled a "hub."** The build spec originally named Saint Martin the hub (map badge, bigger dot, "SXM · HUB" sub-label, every route line drawn from it, "our hub" copy in several places); the client corrected this (Sept/Oct 2026) and no replacement island was named, so the concept was removed rather than reassigned. `content/islands.py` has no `is_hub` field. The regional map (`partials/map_region.html`) instead draws its rings/glow/route lines from a fixed point, `MAP_CENTER` (same coordinates Saint Martin's dot already used, so the visual design is unchanged) — every island, including Saint Martin, gets the same dot size and a route line to that point, except whichever island's own coordinates equal `MAP_CENTER` (currently Saint Martin, which therefore draws no route to itself). Both routes rendering the partial (`index`, `connected`) must pass `map_center=islands_content.MAP_CENTER`. `static/js/map.js` opens the first island by default (not "the hub"). If a real hub island is named later, reintroduce the flag deliberately rather than reverting this.

**Each island card carries a `gateway` stat** (`isle.gateway = {"label", "value"}`, e.g. `{"label": "From USA", "value": "Direct 4h"}`) — this is the third stat row on `/explore-our-islands` cards (`templates/islands_index.html`), replacing an earlier hardcoded "From SXM" row that read the first `CONNECTIONS` chip (which briefly showed nonsensical self-referential data after the airlift rewrite). `access`/`suited_to`/`gateway` are client-authored per island, verbatim — Saint Martin and St Barths' wording is literal client copy (Sept/Oct 2026); the other five reuse the same "From USA · Direct 4h" gateway value as a placeholder pending equivalent copy. The `island_detail.html` "Getting Here" chips no longer hardcode "· from SXM" either — several of those connections (Barbados/Dominica/Grenada route via San Juan/Antigua, not Saint Martin) made that suffix wrong regardless of hub status; the chip's own `note` field already states the real origin.

**The airlift section shows direct flights only.** `content/islands.py` `DIRECT_FLIGHTS` (client-supplied) drives `partials/getting_there.html`: one dropdown per island reading **Direct Flights** when closed, departure city + nonstop time when open, `Seasonal*` on any route whose third tuple item is `True`, and a per-island `note` (St Barths has no long-haul service). The only sea transfer shown here is the client-supplied `boat` tuple on Anguilla and St Barths (`Boat from Saint Martin — 25-30 / 45-60 min`), rendered under the flight grid; never add connecting flights, and keep every other boat option in the regional map's `CONNECTIONS` chips. Selecting a departure city highlights that route in `#route-diagram`, which `static/js/map.js` builds client-side from the `#airlift-data` JSON block (`build_airlift_data()` in `routes/main.py`). The client's disclaimer sits under the diagram. The regional map's island `access` one-liners and its `CONNECTIONS` chips follow the same data: each island with direct service leads with a `Direct` chip built from `DIRECT_FLIGHTS` by `_direct_chip()` (shortest long-haul gateway, regional hops like Santo Domingo only when that is all there is), with the ferry/charter chips kept as the ways in from the SXM hub. The legacy `GETTING_THERE` / `APPROX_TIMES` tables remain only as the assistant's knowledge text.

**Visitor tracking scripts are per domain.** `content/site.py` `TRACKING_SCRIPTS` maps each live host to its ColdIQ / websitevisitors.ai script; `tracking_script_for(host)` strips `www.` and the port, and `app.py` injects the result as `tracking_script` for the one `<script async>` tag in `base.html`'s `<head>`. Any other host — localhost, Vercel previews — gets nothing, so test traffic stays out of the client's analytics; set `TRACKING_HOST` in `.env` to force one. This is the client's outbound-lead tracker and is separate from the in-house visitor analytics in `services/visitors.py`.

**No em dashes in client-facing copy.** The client asked for every "—" removed from visible text (Oct 2026). Scope: body copy, headlines, page `<title>` tags, alt text and aria-labels across `content/*.py` and the public `templates/` — not Python docstrings, code comments, log messages, or the internal `/admin` dashboard, none of which a site visitor ever sees. Prose dashes were rewritten with a colon, comma or period depending on the sentence, never just deleted (that breaks grammar); structural "A — B" pairs (page titles, alt text, aria-labels, step numbers) use " · " instead. `pricing.TIERS` changed shape to avoid an embedded separator: it's now `(key, name, description, multiplier)` 4-tuples, not `(key, "Name — description", multiplier)` — update any new consumer accordingly. A `—` used as a bare "no data" placeholder (e.g. `islands.py` `APPROX_TIMES`, which no longer renders anywhere) was left alone; that's a different character role, not prose.

**Each island's "Getting Here" chips read "DIRECT · from USA"** only for the `Direct` chip (client-specified, Oct 2026); every other mode (`Ferry`, `Flight`, etc.) renders with no origin suffix, since its own `note` already states the real via-point and several of those don't route through the US at all.

**Structured data to JS** goes through inline `<script type="application/json">` blocks rendered from `json.dumps(...)` in the route (`build_map_data()`, itinerary JSON with image URLs, estimator factors) — follow this pattern for new modules.

**SEO metadata has one source.** `content/seo.py` holds every public page's `<title>`, meta description and share image (`PAGES`, keyed by endpoint; island pages come from `island_meta()`), plus the JSON-LD builders (`TravelAgency` + `WebSite` on the home page, `BreadcrumbList` elsewhere: only facts already on the site, no ratings/reviews/hours, no `sameAs` until `SOCIALS` has real URLs). `app.py` `_page_meta()` turns that into `page_meta` (title, description, canonical, absolute og:image, jsonld) and `base.html` renders the whole `<head>` from it, so page templates no longer set `{% block title %}` (only `404.html` does). Canonicals are `SITE_URL` (config, default `https://www.caribbean-incentive.com`) + the clean path, never the query string; `/inquiry/*` re-renders canonicalise to `/lets-connect`. `routes/seo.py` serves `/robots.txt`, `/sitemap.xml` (the `SITEMAP_ENDPOINTS` list + every island, so add new public pages there) and `/favicon.ico`, in its own blueprint so the page-view tracker never counts crawlers. `app.py` also adds security headers (nosniff, Referrer-Policy, X-Frame-Options SAMEORIGIN, Permissions-Policy keeping `geolocation=(self)` for track.js), sends `X-Robots-Tag: noindex` on admin/inquiry/chat/track responses and on any `*.vercel.app` host, and 301s a trailing-slash URL to its slashless route instead of a 404. Titles keep the site's ` · ` separator (no em dashes) and stay under ~65 characters; descriptions under ~160.

## Front end

**Minimal, compact direction (user request).** Keep copy short: pages show headings plus at most a lead paragraph (templates slice long `content/` lists, e.g. `full_paragraphs[1:2]`, `exp.body[:1]`, and trim long strings with the `lead` filter — `text|lead(2)` = first two sentences). Page openings (island pages, Our Story, What We Do, Envision) use the compact `.opening` block — one centred Fraunces lead with the small gold label running inline at its start (`<span class="opening__eyebrow">` inside `.opening__lead`), finished by a small gold diamond. No left/right split, no divider rule. No oversized italic scroll-lit statements (`data-lit`) on pages. Contact / Event Brief / RFP prompts live **only** on `/lets-connect` — reached via the header "Let's Connect" button and menu. Do not add CTA bands, a floating inquiry button, footer inquiry cards or "submit a brief" buttons to other pages. The `cta_band` macro in `partials/section_head.html` is intentionally unused.

No Bootstrap on public pages. Styling is two hand-written files: `static/css/site.css` (tokens, type, motion states, header/menu, heroes, buttons, footer) and `static/css/pages.css` (sections + the five modules). Palette tokens live on `:root` in `site.css`: deep-ocean/lagoon darks (`--ink`, `--abyss`, `--lagoon`), warm sand grounds (`--ivory`, `--sand`), champagne gold, a sparing sunset coral, and signature gradients (`--grad-deep`, `--grad-shell`, `--grad-gold`, `--grad-sunset`). Display type is Fraunces (italic, light); UI/body is Hanken Grotesk.

Libraries (CDN, `defer`): GSAP 3 + ScrollTrigger and Lenis. Every effect that needs them checks they exist — the site must render and work without them.

Scripts:
- `motion.js` — word-splitting (`[data-split]`), reveals (`[data-reveal]`, `[data-clip]`), scroll-lit text (`[data-lit]`), parallax (`[data-parallax]`), pinned horizontal rails (`[data-hscroll]` + `[data-hscroll-track]`, pinned via `.islands-rail__stage` / `.hjourney__pin`), the expanding media scene (`[data-expand]`), counters, magnetic buttons, hover image previews. Exposes `window.CI.lenis` and `window.CI.scrollTo()`; use those for programmatic scrolling.
- `nav.js` — header hide/show, full-screen menu (focus trap, Esc), curtain page transitions, custom cursor (`[data-cursor="Label"]`), inquiry pill visibility.
- `premium.js` + `css/premium.css` (home page only, loaded from `index.html`) — scroll progress line, hero cursor spotlight + headline depth drift, 3D coverflow/tilt/glare and staggered 3D entrance on the island rail, and clip-path band reveals on `.wwd`/`.possible`. All additive; reduced-motion disables motion. (The canvas ocean-wave dot field that used to sit under the map was removed at the user's request, Oct 2026; don't reintroduce it.)
- Module scripts: `hero.js` (WebGL shader crossfade with CSS-layer fallback), `map.js` (map + "getting there" accordion), `island.js`, `itinerary.js`, `estimator.js`, `forms.js`, `testimonials.js`, `chapters.js`.

**Motion must default to visible.** `motion.js` splits text first, *then* adds `reveal-init` to `<html>`, and only that class hides pending elements; the entry curtain is a pure-CSS animation gated on `html.js`. Never invert this order. Clipped media (`[data-clip]`) are observed through their parent element because Chrome's IntersectionObserver treats an element's own `clip-path: inset(100%)` as fully hidden.

**The five interactive modules** keep their original element IDs (JS depends on them): hero (`partials/hero_video.html`), regional map + access accordion (`partials/map_region.html`, `partials/getting_there.html`), island detail (`island_detail.html`, per-island data in `content/islands.py` `panels`/`cards`; map positions + label side in each island's `map`), itinerary (`partials/itinerary.html`), estimator (`partials/estimator.html` — island pills and tier cards are radios in `[data-drives]` groups that set the visually hidden `#est-island` / `#est-tier` selects the maths reads; keep those selects).

## Known constraints (intentional, not bugs)

- Photography is free stock (Unsplash), not real Caribbean Incentive assets. Swappable via `content/media.py`. No `picsum.photos` anywhere.
- Sellsy is configured; SMTP/Teams/WhatsApp may not be. `.env.example` documents each key and its fallback.
- `GETTING_THERE` / `APPROX_TIMES` (10 rows) no longer render anywhere — the airlift accordion uses `DIRECT_FLIGHTS` (7 islands, the ones with direct service). They are kept because `services/chatbot.py` folds them into the assistant's knowledge base.
- `static/css/brand.css` is no longer loaded anywhere (legacy).

## Admin

`/admin` (sign-in from `ADMIN_USERNAME` / `ADMIN_PASSWORD` in `.env`, compared in constant time; blank disables sign-in) is a dark "command centre" with its own self-contained `static/css/admin.css` (no Bootstrap; Bootstrap Icons font only) and `static/js/admin.js` (hand-rendered SVG sparklines, area chart with hover tooltip, donut, count-ups, visitor filters). **No demo data — every admin figure is live.** Visitors (`services/visitors.py`: **no per-click journey is stored** — only `caribbean_incentive_visitors` (one row per browser with running totals: sessions, pages, `module_ms` JSONB, last page, `saw_connect`) and `caribbean_incentive_daily_stats` (one row per day: sessions, pageviews, bounces, session seconds, JSONB counters for hours/modules/islands, merged with the `caribbean_incentive_jsonb_add` SQL function). Fed by a `ci_vid` cookie, the page-view `after_app_request` hook in `routes/track.py` for public `main` pages (bots skipped), module dwell beacons from `static/js/track.js` to `POST /t`, and `identify()` calls in `routes/inquiry.py` that mark a visitor Converted; writes go through a background queue; location is an enrichment layer in `services/geo.py`: every visitor gets an approximate IP location (`location_method = 'ip_approximate'`) at their first tracked page view, from Vercel's free `x-vercel-ip-*` headers (read in-request into `geo_hint`), else ipinfo.io when `IP_GEOLOCATION_API_KEY` is set, else `GEOIP_URL`; both failing stores `'unknown'`, retried after 24 h. `static/js/track.js` then asks the browser for GPS **once per browser** (8 s after load, HTTPS only, remembered in `localStorage`, a denied permission respected) and posts it to `POST /t/location`, which identifies the visitor by the `ci_vid` cookie only (never a client-sent id), validates the coordinates and stores `'browser_gps'` with accuracy, named by reverse geocoding (`REVERSE_GEOCODE_URL`, Nominatim). IP results never overwrite GPS, and IP coordinates are stored without an accuracy figure. The Visitors table shows "City, Country" plus 📍 Precise / ≈ Approximate (never raw coordinates); the visitor page shows coordinates, accuracy and update time. Columns: `location_method`, `latitude`, `longitude`, `location_accuracy`, `country_code`, `timezone`, `location_updated_at` (added idempotently in `SCHEMA`; `city`/`region`/`country` reused). Dashboard/Analytics figures come from `services/analytics.py` over a rolling 14-day window. `content/admin_mock.py` now only holds `BUDGET_MIDPOINTS`, pipeline stages and helpers. **Speed:** the database is ~400 ms away, so each admin page does exactly one round trip — routes call `_load(**queries)` in `routes/admin.py`, which merges the page's SELECTs with the sidebar counts into one `store.query_batch()` statement (JSON-aggregated, autocommit, no BEGIN/COMMIT). Add new admin reads as query builders passed to `_load`, never as separate queries. **Every admin list is paginated on the server** (Visitors, Event Briefs, RFP Uploads, Callbacks, Sellsy): routes read `_list_args()` (`page`, `per` ∈ 10/25/50/100, `status`, `q`), fetch one page with LIMIT/OFFSET plus a COUNT and per-status counts in the same `_load` batch, build the pager with `_paginate()`, and redirect an out-of-range page to the last one. Templates use the `toolbar()` (status chips as links + GET search) and `pager()` macros from `templates/admin/_pager.html`; `page_url(**changes)` rebuilds the current URL. Status changes return to the referring page/filter. Follow this for any new list. The **Sellsy** tab (`/admin/sellsy`, `templates/admin/sellsy.html`) reads the configured pipeline from the Sellsy API via `sellsy.pipeline_snapshot()` — an in-memory snapshot (opportunities with embedded company/contacts/individual, stage totals) refreshed on a background thread when older than 60 s and warmed on every admin page load, so the page never waits on Sellsy; `?refresh=1` forces a sync. Chart series reach JS via the `#admin-chart-data` JSON block. **Export report** (dashboard button → `/admin/export.xlsx`, `export_report` in `routes/admin.py`) builds a branded workbook with `services/report.py` (openpyxl): an Overview sheet (KPI tiles, native Excel charts, summary tables) plus Daily, Event Briefs, RFP Uploads, Callbacks, Visitors and Sellsy Pipeline sheets, from one `_load` round trip and the in-memory Sellsy snapshot. It reuses the dashboard's shaped records and `analytics.build`, never stores anything, and leaves storage plumbing (file URLs/paths) out like the e-mails.
